## なぜ Perch？

Windows でバックグラウンドプロセスや長期間稼働するサービスを管理するのは、思ったより面倒です：

- **Task Scheduler** はデフォルトで長期間稼働するプロセスを強制終了します（セッションタイムアウト、プロセスツリーの終了、ログインセッションへの依存）— もともと daemon 向けに作られていません。
- **NSSM / WinSw / Shawl** はサービスごとに1つの wrapper が必要。ダッシュボードも中央ビューもなく、N 回登録しなければなりません。
- **PM2** は Node.js ランタイムが必要で、daemon がアイドル時でも 40–80 MB を消費し、Windows では二級市民です（起動が不安定、レジストリのハックが必要）。
- **Supervisor** は Windows では動作しません。

Perch がこの隙間を埋めます：**一度登録すれば、すべてを管理。** 単一のネイティブサービスがすべてのプロセスを監視し、Web UI を提供し、目立たず動作します。

## 機能

- **シングルバイナリ** — ランタイム不要、依存関係なし。Web UI は実行ファイルに直接組み込まれています。
- **ネイティブ Windows サービス** — 一度登録すれば、起動時に開始、ログアウト後も継続、Session 0 で実行。
- **低メモリ使用量** — Rust でコンパイル、単一の supervisor プロセス。アイドル時の常駐メモリは 4–5 MB 程度、PM2 の 40–80 MB と比べて少ない。
- **Web UI 内蔵** — ブラウザからステータス確認、プロセスの開始/停止/再起動、ログの tail が可能。コンソールだけでなくリモート管理に対応。
- **自動再起動** — クラッシュしたプロセスは自動的に再起動され、バックオフは設定可能。
- **スケジュールタスク** — cron 形式の周期ジョブのスケジューリング。
- **日次ログローテーション** — アプリケーションログは実行ファイルと同じ場所の `logs/perch.YYYY-MM-DD.log` に書き込まれ、パイプ区切り形式。
- **インタラクティブメニュー** — exe をダブルクリックして、サービスのインストール/アンインストール/開始/停止、Web UI の起動が可能。UAC 昇格は必要に応じて実行。

## ステータス

Perch はリリース済みで、現在のバージョンは v0.1.0 です。0.x 系のプロジェクトのため、インターフェースや設定は今後のバージョンで変更される可能性があります。

## クイックスタート

`perch.exe` をダブルクリックし、メニューから `5) Open Web UI (Web UI を開く)` を選択 — Perch はデフォルトの `perch.toml`（`demo` プロセスとトークン `change-me` を含む）を自動生成し、サーバーを起動します。

またはコマンドラインから：

```
# フォアグラウンドで実行（Ctrl-C で停止）
perch run

# Perch を Windows サービスとして登録（管理者権限が必要）
perch install
perch start

# Web UI を開く
http://127.0.0.1:9000
```

デフォルトのトークンは `change-me` です — 実際の使用前には `perch.toml` で変更してください。

### 初回起動時の注意：Windows SmartScreen

配布されているバイナリはコード署名されていないため、初回起動時に Windows SmartScreen が **「Windows によって PC が保護されました」** と表示することがあります。署名されていないオープンソースツールでは想定される動作です。**詳細情報 → 実行** をクリックして続行してください。（`.zip` をダウンロードすればブラウザのダウンロード警告は回避できますが、初回起動時の SmartScreen の表示は別の問題であり、有料のコード署名証明書を使わない限り回避できません。）

### 自分のユーザーアカウントでサービスを実行する

Perch のサービスはデフォルトで `LocalSystem` として実行され、システムレベルの環境変数しか参照できません。ユーザーレベルの PATH（`HKCU\Environment`、例えば `uv` や `pipx` でインストールした CLI が置かれる `%USERPROFILE%\.local\bin` など）は見えません。管理対象のプロセスやスケジュールタスクがユーザーレベルの環境変数に依存するコマンドを呼び出す場合、自分で実行すれば動くコマンドでも、サービス経由では "command not found" になります。

サービスを `LocalSystem` ではなく自分のアカウントで実行するには：

1. `Win+R` を押し、`services.msc` と入力して Enter。
2. **Perch Process Manager** を見つけ、右クリックして **プロパティ** を選択。
3. **ログオン** タブを開く。
4. **このアカウント** を選択し、Windows アカウント（ローカルアカウントなら `.\ユーザー名`、ドメインアカウントなら `ドメイン\ユーザー名`）とパスワードを2回入力する。
5. OK をクリックすると、Windows がそのアカウントに「サービスとしてログオン」権限を自動的に付与します。その後サービスを再起動してください（右クリック → 再起動、または `perch stop` の後に `perch start`）。

これでサービスが自分のユーザーとして実行されるようになり、子プロセスはユーザー PATH を含む自分の環境変数をすべて引き継ぎます。

注意点：
- 後で Windows のパスワードを変更した場合、同じログオン タブでパスワードを更新するまでサービスは起動に失敗します。
- アカウントを変更せずに回避する方法として、プロセス/タスクのコマンドで実行ファイルを絶対パスで指定する、または必要な変数を明示的に設定する、という手もあります。

## セキュリティ

管理エンドポイントは任意のプロセスを開始・停止できるため、**非常に高い権限**を持ちます。Perch はデフォルトで `127.0.0.1` にバインドし、アクセストークンを要求します。管理ポートを信頼できないネットワークに公開しないでください。
